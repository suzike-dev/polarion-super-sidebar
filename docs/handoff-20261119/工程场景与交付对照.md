## 同一条需求的贯通验收

用隔离工作项和可写的模型、测试副本建立已核准基线。先改需求中的判据，再独立改变模型中的对应参数，分别验证两种来源。每次记录触发原因、原文位置、模型路径/块/参数、测试用例和证据版本。选择以需求或模型为准后预览差异，批准后回读，再运行关联测试。冲突、缺权限、缺测试或失败应停在可处理状态。最后在同一工作项调整说明、表格和原图，重跑评审，核对项目经验和变更时间线。

原工作流文档里的版本号早于两轨合并。跨线排序以 [ROADMAP.md](../../ROADMAP.md) 为准。已批准的最终能力持续保留；每项完成以对应用户动作及复验记录为依据。

## 2026-11-19 AI 预审真机跑通（根因：引擎未注入）

连续三次预审卡在“预审中”，期间最小回合与同提示词普通 run 均正常。逐层对比后定位根因：**Service 构造只做了 `engines.reviews = reviews`，从未把 engines 注入 Reviews/Meetings**；`reviews.start` 里 `this.engines?.execute()` 静默空转，而 `store.startRun` 对无排队会话直接置 `running`——于是留下“running 但无人执行”的僵尸记录。

修复：
- Service 构造补 `reviews.engines = engines; meetings.engines = engines;`
- Reviews/Meetings.start 在缺引擎时直接抛 `ENGINE_UNAVAILABLE`（不再先建 run 留僵尸）
- 回归测试锁定：缺引擎拒绝且不留记录；有引擎时 execute 被真实调用、记录持久化 runId
- 配合上一批停滞自愈：即使未来再出现挂起，120s 后也会显式失败可重试，而不是永远“预审中”
